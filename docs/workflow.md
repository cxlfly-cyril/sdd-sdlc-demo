# 开发与交付流程

## 需求自动跟随

本节由 Agent 执行。用户用自然语言提出需求，无需指定 Specs、Changes 或 AC 编号。工作在每次任务开始时触发，不依赖用户重复提醒。

1. **判断影响**：读取当前相关规格、实现和测试，识别受影响的验收编号及约束。把需求分类为 visual（外观）、interaction（保留预期行为的交互调整）、behavior（预期行为变化）、bugfix、infrastructure 或 documentation。混合修改以影响最大的类别记录，或拆成独立变更。完成条件：每项修改都能解释为何需要或无需更新规格。
2. **形成记录**：运行 `npm run change:new -- short-name` 创建新目录。由 Agent 填写 change.json 的用户需求、修改文件、规格影响、验收编号；record.md 简要记录方案和验证。小改动只需这两个文件；复杂变更可附 intent/plan/tasks。完成条件：文件范围覆盖本次全部修改，历史记录不替代新记录。
3. **处理规格**：visual 通常保留业务规格；interaction 核对触屏、键盘、焦点、提示及状态变化是否仍符合预期；behavior 先更新规格，保留稳定编号并新增必要验收；bugfix 保留正确规格并补回归测试。基础设施和文档修改说明与业务规格的关系。用户明确要求的新行为即可作为变更依据；只有歧义、目标冲突或重要取舍需要用户决定，并继续处理不依赖该决定的工作。完成条件：记录中有可审阅的差异或不更新原因。
4. **实现与验证**：按规格实现，同步受影响测试和 traceability。产品修改跑现有完整业务验收；样式/交互另外检查桌面、手机、键盘及相关交互，不为了纯视觉变化机械新增测试。缺陷回归先证明能暴露问题。基础设施/文档采用适用检查。执行 `npm run check:change`，将实际命令、结果和证据写入记录，尚未执行的检查明确列出。完成条件：检查通过且证据足以评估修改效果。
5. **交付审阅**：检查最终 diff 与规格语义是否一致，主动寻找遗漏的提示、持久化、同名任务隔离和存储降级影响。在 PR 中链接新的 Changes，说明规格影响和验证结果。完成条件：CI 通过，结果可审阅；最终答复指出仍需用户决定或未验证的内容。

change.json 是 CI 可读取的交付清单；record.md 是简短事实记录。`check:change` 检查新记录、修改覆盖、编号、规格更新声明和验证字段，不自动判断分类是否诚实或业务语义是否正确。语义一致性由 Agent diff 审查、业务测试和人工 PR 审阅共同确认。

## PR 与 CI

PR 关联 Issue（如有）、验收编号和验证证据。CI 工作流先执行变更记录检查，再执行追溯结构检查、类型检查、单元测试、构建与浏览器测试。查看 Acceptance checks 通过后人工审阅合并；main 已启用分支保护，要求 PR、Acceptance checks 通过且分支与 main 同步；该要求也适用于管理员。

## 演示发布

main 的验收与生产构建浏览器检查通过后，发布 GitHub Pages；部署后验证页面资产并执行线上浏览器验收。线上验收失败将标记工作流失败，但不自动回滚。演示发布以人工合并作为批准，生产环境另行定义审批。

## 可用性监控与维护

Pages monitor 定时检查页面与资产；失败时去重记录事件 Issue，恢复时附证据关闭。运行日志和 monitor-result 保存检测结果。

后续 Agent 诊断并建立新变更：实现缺陷补回归测试，需求变化更新规格。修复通过 PR 审阅，发布后确认恢复。

默认 GITHUB_TOKEN 创建的普通事件通常不会触发另一工作流；采用同一工作流调用处理步骤或显式 workflow_dispatch，验证实际触发链。

## 最终验收

演练一次需求变化和一次隔离环境故障，提供规格版本、测试结果、PR、部署及恢复证据，再声称闭环完成。
